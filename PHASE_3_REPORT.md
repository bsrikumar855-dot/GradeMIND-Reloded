Design guarantees, each backed by a test:
- **OCR text never reaches a verdict.** An import-linter contract forbids the grading modules (`scoring`, `grading`, `evaluation`, `routes/grading*`) from importing any OCR module, directly or indirectly; `tests/test_ocr_isolation.py` plants imports to prove the contract fires. Equivalence tests show grading output is identical with and without OCR and with and without corrections.
- **Grading never waits for OCR.** Readiness is `pages_ready` (page images exist), not job completion. A dead or slow OCR service leaves the booklet gradable.
- **OCR never edits the page image.** Student text is data: stripped of bidi / zero-width / control characters on display, rejected on write, rendered escaped; a repo-wide test forbids raw hidden characters in source files.
- **Corrections are labelled data, append-only.** Database triggers refuse UPDATE/DELETE on `ocr_runs`, `ocr_lines` and `line_corrections`; stale edits get 409 (optimistic concurrency).

## What the OCR actually read

**Synthetic printed page** (Helvetica, generated by `tests/helpers/pdfgen.py`; read by PP-OCRv6 medium det+rec on CPU, CI run `38038114654`):

| Known line | Machine reading | Score |
|---|---|---|
| Photosynthesis needs light and water. | identical | 0.9974 |
| Plants make their own food in the leaves. | identical | 0.9999 |
| Chlorophyll gives leaves their green colour. | identical | 0.9976 |

Character error rate on this page: **0 errors in 122 characters (3 lines)**. That is a smoke test of the pipeline on the easiest possible input (clean printed text, one font, no ruling, no noise). It is not an accuracy measurement and must not be quoted as one.

**Real handwritten sheets** (Phase 0b, `PHASE_0B_REPORT.md`; unchanged by this phase): best single engine `b_v6` (the same PP-OCRv6 family used here) raw line CER **0.425 [0.266, 0.621]**, 7 transcribed pages from 2 sheets, ground truth `AGENT_VERIFIED` (not owner verified), differences between engines `NOT_DISTINGUISHABLE`.
So on handwriting expect roughly four characters in ten wrong. **No CER has been measured on handwriting through this product, and there is no data in this repository that would allow one**: the corrections table is the mechanism that will eventually produce it, and today it holds E2E test rows only.

The 0.80 low-confidence threshold in the panel is a guess, not a calibrated value. Printed text scores 0.997+, so a score near 1 is not evidence of correctness on handwriting (Phase 0b recorded silent errors).

## Known gaps (not hidden)

- **Handwriting is unvalidated** (see above). No handwritten page has been read through the product; real sheets 001/002 were not used in the E2E.
- **Throughput:** the OCR stage holds a worker slot for a whole booklet (about 12-14 s per page, one page at a time in the service; 48-49 s per 2-page booklet when three were queued in CI). Worker slots were raised from 2 to 6 as a stop-gap. Bulk upload of many booklets will queue behind OCR. A dedicated OCR queue is the proper fix (decision below).
- If the OCR service is unavailable the stage fails with `ocr_unavailable` (grading unaffected); re-reading needs the examiner's "retry" or the OCR retry endpoint. The sweeper re-sends only lost `QUEUED` jobs, not failed ones.
- No admin UI to create users or assign examiners (CLI `create-user` and API only).
- The line crop is not de-skewed; a skewed page gives a skewed crop. The polygon and page hash are stored so a later builder can re-crop.
- A crop can be orphaned in storage if the database commit of a correction fails after the upload (no garbage collection yet).
- Touch devices and screen readers are untested; keyboard use is covered by Playwright for drawing and the panel, not audited.
- The dataset export was exercised on a handful of rows. Untested at scale; `public` scope still needs the D20 redaction review before anything is published.
- Only the first page of the synthetic booklet carries text in the E2E; multi-page booklets with several answer boxes per page are covered by API tests, not the browser test.
